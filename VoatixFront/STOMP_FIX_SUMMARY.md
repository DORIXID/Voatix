# STOMP WebSocket Connection Fix Summary

## Проблема
STOMP соединение некорректно работало из-за использования `username` (nickname) как основного идентификатора вместо `userId`. Это приводило к ошибкам в маршрутизации сообщений и управлении подписками.

## Решение
Переделана вся логика работы с WebSocket для использования `userId` как основного и надёжного идентификатора.

## Изменённые файлы

### 1. [websocket.service.ts](src/app/service/websocket.service.ts)

**Изменения:**
- Добавлен интерфейс `MessageReceivedEvent` с полями `userId`, `chatId`, `chatNickname`
- Обновлён метод `markAsRead()`:
  - Теперь **ВСЕГДА** отправляет `userId` в качестве идентификатора
  - Никогда не отправляет `username` на бэкенд
  - Логирует отправляемые данные
- Обновлена сигнатура `notifyMessageReceivedInChat()`:
  - Теперь принимает второй параметр `userId?: number`
  - Передаёт userId в событие
- Обновлена возвращаемая типизация `getMessageReceivedInChat$()` для новой структуры события

### 2. [messages-form.component.ts](src/app/messages-form/messages-form.component.ts)

**Изменения:**
- Обновлен метод `selectChat()`:
  - Теперь проверяет наличие `userId` перед отправкой `markAsRead`
  - Если `userId` отсутствует, логирует предупреждение
- Обновлен метод `selectChatByNickname()`:
  - **Приоритет 1**: Поиск по `userId` (если передано)
  - **Приоритет 2**: Поиск по `nickname` (fallback)
  - Создание нового чата использует `userId` как основной идентификатор
- Обновлена подписка `subscribeToMessageReceivedInChat()`:
  - Ищет чат сначала по `userId`, затем по `nickname`
  - Корректно обрабатывает оба варианта идентификаторов

### 3. [chat-detail.component.ts](src/app/chat-detail/chat-detail.component.ts)

**Изменения:**
- Обновлен метод `subscribeToMessages()`:
  - **ПРИОРИТЕТ 1** (НАДЁЖНЫЙ): Сравнение по `senderId` и `chatUserId`
  - **ПРИОРИТЕТ 2**: Проверка по `receiverId` для входящих сообщений
  - **ПРИОРИТЕТ 3**: Fallback на сравнение `nickname` (старый формат, менее надёжный)
  - **ПРИОРИТЕТ 4**: Принятие по умолчанию если нет идентификаторов
  - Добавлено детальное логирование для отладки
  
- Обновлен вызов `markAsRead()`:
  - Всегда использует `userId` если доступен
  - Fallback на `nickname` если `userId` отсутствует
  
- Обновлен вызов `notifyMessageReceivedInChat()`:
  - Теперь передаёт `userId` в качестве второго параметра
  
- Обновлен метод `markMessagesAsRead()`:
  - Всегда использует `userId` для отметки прочитанных сообщений

## Результаты

✅ **Надёжная маршрутизация сообщений**: Сообщения теперь корректно направляются в нужный чат на основе `userId`

✅ **Правильное управление уведомлениями**: Уведомления о прочтении отправляются с правильным идентификатором

✅ **Улучшенное логирование**: Добавлены подробные логи для отладки проблем с соединением

✅ **Backwards compatibility**: Код по-прежнему поддерживает старый формат с `nickname` в качестве fallback

## Тестирование

Для проверки можно использовать приложенный [WORKINGtest.html](../WORKINGtest.html):

1. Скопировать файл в браузер
2. Вставить JWT токен
3. Указать receiverId (userId получателя)
4. Отправить тестовое сообщение
5. Проверить логи в браузере для подтверждения корректной маршрутизации

## Важные замечания

⚠️ **Убедитесь, что:**
- Бэкенд отправляет `userId` или `senderId` в сообщениях
- JWT токен содержит поле `userId` или `id`
- Клиент всегда отправляет `receiverId` при отправке сообщений
- STOMP подписки используют правильные destinies с userId
